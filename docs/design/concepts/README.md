# 概念圖（三個方向）

由本機 `codex` CLI（`codex-cli 0.164.0`，模型 gpt-6-astra，`codex exec -s workspace-write`）
依同一份內容需求寫成純 SVG 線框，每張左側為 `/g/:id` 群組頁、右側為記帳 bottom sheet。
codex 無法產生點陣圖，只能寫 SVG，因此是低保真線框，不含配色與字體。

## A · 卡片式 — `a-cards.svg`

- 強調：資訊分區明確，每張卡片對應 API 回應的一段（balances / settlement / expenses），React 元件一對一。
- 犧牲：垂直空間，三張卡片疊起來首屏只能看到餘額與 settle；settle-up 沒有被特別突出。
- 一小時作業＋現場加功能：**最適合**。加「記錄還款」就是 settle 卡多一顆按鈕，加「多幣別」就是金額欄旁一個 select。

## B · 票卡式 — `b-ticket.svg`

- 強調：settle-up 當主角做成登機證般的票卡，虛線撕票線把每筆還款變成存根；金額超大字，記帳時很有「付費」的實感。
- 犧牲：裝飾性 CSS（打孔、虛線、雙欄表單）要花時間調；餘額改成橫向小格，四人以上就要捲動或換行；與評分重點無直接關係。
- 一小時作業：風險偏高，若現場要加欄位，雙欄表單先壞。適合作為時間充裕時的視覺升級。

## C · 清單式 — `c-list.svg`

- 強調：最高資訊密度，像 iOS 設定頁；表單用「Paid by Kai · split equally」一行摘要收納次要控件，最接近 Splitwise 的最短記帳路徑。
- 犧牲：各區塊只靠小標分隔，餘額與 settle-up 視覺上混在一起，「誰欠誰一眼看懂」反而被削弱；展開／收合摘要列多一個狀態要管。
- 一小時作業：可行但摘要列的展開邏輯容易做半套，現場加功能時每個新欄位都要決定「放摘要內還是外」。

## 決定

採 **A 卡片式**，並借用 B 的一個點：settle-up 卡片提到餘額之上、用 accent 邊框當主角；
借用 C 的一個點：sheet 內的分法預覽永遠顯示每人分到多少與餘數歸誰。詳見 `../mockup.html`。
